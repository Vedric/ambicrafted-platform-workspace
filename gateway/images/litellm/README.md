# Qualified LiteLLM derivative

## OpenTelemetry parser backport — 2026-10-23

The `1.104.4-stable-security.20261023.1` derivative applies the official
[CVE-2026-114603 fix](https://github.com/open-telemetry/opentelemetry-python/commit/d5224bf4ffdf2aee1b592ad238dcc32ca957f26b)
to the two affected OpenTelemetry API source files. The
[vendor advisory](https://github.com/open-telemetry/opentelemetry-python/security/advisories/GHSA-xcq7-p3pf-p88h)
describes quadratic processing of malformed `tracestate` whitespace. The
backport uses linear splitting/whitespace handling and rejects combined
propagation headers longer than 8,192 characters while preserving a valid
`traceparent`.

This is a **source backport to API 1.33.1**, not an upstream 1.45.1 installation.
The installed SDK and semantic conventions require API 1.33.1, and LiteLLM's
`proxy-runtime` extra pins the complete 1.33.1/0.54b1 cohort. The inspected
official LiteLLM 1.104.5 and 1.106.2 source releases retain those constraints.
Replacing only the API would break the declared dependency contract; replacing
the whole cohort would introduce unrelated changes across twelve minor versions.

`backport_otel.py` refuses unexpected original source, distribution metadata or
RECORD bytes before writing any file. It verifies the exact expected output
hashes, preserves the original Apache-2.0 notices, marks the source modification,
updates the two source entries in RECORD and removes their generated bytecode
caches. The distribution version and METADATA remain unchanged. The runtime
attestation is `/usr/share/ambicrafted/otel-tracestate-backport.json`; patching
tools and test fixtures stay outside the final image.

The build runs with networking disabled:

- Four negative/source guards, including changed source, metadata and RECORD
  refusal before any installed file is changed.
- All 25 parser/propagator tests from the retained upstream 1.33.1 source, plus
  all four security regression methods added by the fix commit. The downloaded
  vendor files are unmodified, pinned by SHA-256 and accompanied by their license.
- Three installed-runtime checks covering the unchanged cohort/metadata,
  truthful source/RECORD hashes and the actual LiteLLM tracing callback.

An initial attempt to run the entire 1.45.1 suite failed on its unrelated
`TraceState.update()` behavior at capacity. The backport preserves the 1.33.1
contract and adds the security fix's tests; it does not claim compatibility with
every intervening upstream API change. That initial failed result is retained
in the private qualification evidence.

Exact local image:
`sha256:8a2f4e749f4094d00ad637d2cd7412d49a9037900c6f7eac2eb11f5c4946fcf4`.
All 199 Python distribution versions are unchanged. Of 19,732 non-bytecode Python
files, 19,729 match the preceding derivative; the other three are the two
affected source files and their RECORD. In separate containers limited to one CPU, a direct
`TraceState.from_header()` call with 100,000 whitespace characters took
4.306 seconds for spaces and 7.220 seconds for tabs before the fix, versus about
0.00002 seconds afterward. These are bounded parser measurements, not gateway
response-time or overall capacity guarantees. Single and combined headers at
8,192 characters remain accepted; 8,193-character headers are discarded without
losing their valid trace parent.

The fresh 23 October Trivy database still reports **one MEDIUM occurrence**, with
API 1.33.1 and upstream fixed version 1.45.1. No advisory, package, path or
severity is suppressed, and no version is relabeled. The zero-findings and
Python-audit results in the dated 22 October sections below are historical.

An isolated 87.653-second service check passes authentication, restricted aliases,
real local embeddings, key preservation through migration/restart, restoration
into an independent old-version database, and actual OTLP delivery to Tempo.
Exported spans preserve their caller's parent, retain valid `tracestate` and
discard an oversized header. All test containers, volumes and the network are
removed. This **limited profile is not full inference qualification**:
`profile_passed=true`, `passed=false`, `generation_requested=false`.

The preceding full gateway check timed out during generation. A direct synthetic
request to the same model service, bypassing LiteLLM, also timed out at 30 seconds;
a direct embedding request succeeded in 0.071 seconds. Host inference diagnosis
is separate from this parser correction. At that initial checkpoint, full
streaming/structured generation, personal deployment and release acceptance
remained pending. The later complete CPU qualification is recorded below; it
does not resolve GPU recovery or release acceptance. The gateway timeout was
not increased to turn a failed availability check green.

```sh
docker buildx build --load --platform linux/amd64 \
  --build-context trust-policy=gateway/images/trust-policy \
  --tag ambicrafted/litellm:1.104.4-stable-security.20261023.1 \
  gateway/images/litellm
uv run --locked --project apps/control-api python gateway/images/litellm/qualifier.py \
  --old-image ambicrafted/litellm:1.104.4-stable-security.20261022.2 \
  --new-image ambicrafted/litellm:1.104.4-stable-security.20261023.1 \
  --postgres-image ambicrafted/postgres:16.15-alpine-security.20261022.2 \
  --tempo-image ambicrafted/tempo:3.0.3-security.20261021 \
  --output /absolute/private/new-gateway-qualification.json
```

`--embeddings-only` requests the explicitly limited diagnostic profile and keeps
the full `passed` gate false, even when its checks succeed. Re-run the command
without that flag to qualify actual streaming and structured generation.

## Complete generation and trace-arrival qualification — 2026-10-23

Following a scoped application restart, generation became available through
CPU fallback while the host GPU fault remained open. The full service exercise
revealed an early-exit defect in the verifier: Tempo could return auth/pre-call
children before the SERVER parent. A diagnostic read 200 ms later observed the
correct parent in that same trace. Waiting for any span was not sufficient.

The verifier now waits for the required caller-parent span within the original
60 polls/one-second interval. It immediately rejects incorrect trace identity or
parent state and reads only actual OTLP span collections, not cross-trace links.
Seventeen tests cover acceptance guards, partial arrival, missing parents,
incorrect state/identity, protobuf encoding and malformed data. Two negative
comparisons demonstrate the prior verifier's failures.

The complete exercise then passed in 120.878 seconds using the exact new image
above and actual prior live image `sha256:50bcffed7f60102fde9620be6a9863ce1746fd856f71bf9a36a1d4e088cdd914`.
All seven checks are true, including structured generation, streaming and real
trace delivery; migration, restart, separate-volume rollback and cleanup pass.
Report SHA-256: `ba0c4a57a4d7f54d3890ab9d6a4a74a66f025aa0faf8b5daea37f0cbce21dd81`.
The corrected verifier's SHA-256 is
`3fdc98bdc4681006945a1873f2fade7ae070ced966362b73102aa49e879c5b01`.
The preceding failures and limited profile remain preserved. This is functional
qualification of the gateway image on CPU; it does not certify GPU recovery,
conversational latency, installation on the live data or release acceptance.

## Available native-library fixes — 2026-10-22

The `1.104.4-stable-security.20261022.2` derivative upgrades only the four
installed Wolfi glibc packages from **2.44-r6 to 2.44-r8**, retaining the CA
and PDF corrections below. Wolfi's [primary security feed](https://packages.wolfi.dev/os/security.json)
identifies fixes for CVE-2026-8674, CVE-2026-86805, CVE-2026-89092 and
CVE-2026-95818. They concern resolver, loader and local process behavior;
the previous sixteen MEDIUM occurrences were four advisories across four
packages. Their severity was not a reason to leave compatible fixes unapplied.

All four APK archives are pinned by exact URL and SHA-256 in the Dockerfile.
Wolfi authenticates these archives through its **signed repository index**;
they do not carry individual APK signatures. APK verifies the index using
the base image's trusted public keys and authenticates each archive against
that index. Installation uses a local build-only repository with networking
disabled. There is no `--allow-untrusted`. A negative check with an empty
key directory refuses the same repository. The signed index is fetched at
build time, so removal of a pinned package by the vendor fails the build.

Exact qualified local image:
`sha256:e35ae0923cb2390347ef3ecec1db023325c28f20059e19f151664ca4f3b0fffc`.
The same 22 October Trivy database reports **zero findings at all five
severities**. All 3,515 non-bytecode LiteLLM files match the preceding image;
the exact native CA bundle, 118 effective OpenSSL anchors and 63 installed
pypdf wheel files also pass their independent checks. The isolated gateway
qualifier passes authentication, restricted aliases, key migration, streaming,

## Targeted trust correction — 2026-10-21

The 21 October image additionally distrusts the exact compromised emSign ECC
G3 root in its actual operating-system trust stores. See the shared
[trust policy](../trust-policy/README.md) for the fingerprint, native Java handling,
unchanged package inventory, qualification evidence and limits. This is a local
trust-policy change, not a claim that the vendor CA package was upgraded.
The named build context below contains only public policy code and certificates;
it is required when building manually. Compose and the image scanner supply it
explicitly. Existing application binaries and features are unchanged by this step.

The Dockerfile uses the immutable official `main-v1.104.4-stable` image and
replaces only `aiohttp` 3.14.3 → 3.14.4, its required `yarl` 1.25.1 dependency,
and `certifi` 2026.4.22 → 2026.10.19.
The old yarl 1.23.0 does not meet the corrected aiohttp requirement. The aiohttp/yarl wheels
are official PyPI CPython 3.13 Linux x86-64 artifacts; certifi uses the universal
Python wheel. All three artifacts are pinned by URL and SHA-256.
Installation uses verified uv 0.13.4, offline, with no dependency re-resolution.
No build tools or wheels are copied into the final runtime.

This deliberately follows a stable upstream line. It does not adopt an unrelated
feature release merely because its version number is higher. Upstream application
code, database migration machinery and package metadata remain intact.

The historical images below were tested with their contemporaneous recipes.
Use the current build and qualification commands at the top of this document
for the new derivative; do not rebuild this Dockerfile under an older tag.

The qualifier creates its own network, databases and credentials. It tests
anonymous/wrong-key rejection, the confidential alias allowlist, preservation of
a real virtual key through migration and restart, real local streaming/embeddings,
a JSON-schema-constrained response, and restoration of a pre-upgrade dump into a
separate old-version database. The structured-response check validates transport
compatibility and the returned shape, not factual correctness.
Only synthetic prompts reach the configured local model. It never restores or
modifies the workstation database. It needs Docker, the reviewed gateway config
and local model availability; it does not prove every LiteLLM provider works.

The earlier 20 October scan found 0 CRITICAL / 0 HIGH and 16 MEDIUM occurrences.
That database predates the newly published
[certifi CA compromise advisory](https://github.com/certifi/python-certifi/security/advisories/GHSA-6q48-6c7w-9gw2),
so that result does not clear the old image of the later-disclosed issue.
The [PyPA record](https://github.com/pypa/advisory-database/blob/main/vulns/certifi/PYSEC-2026-4320.yaml)
recommends 2026.10.19, which removes the affected emSign ECC G3 trust anchor
while restoring the three unaffected emSign roots removed by 2026.10.18.

The 21 October build installs the actual official wheel offline and verifies
the complete installed PEM SHA-256 and the effective OpenSSL trust anchors.
The affected root must be absent and the three unaffected roots must remain.
`verify_certifi.py` fails closed on a different version or bundle. The certifi bundle is never edited locally, and no scanner inventory is suppressed.
The separate OS trust correction is described above.
This checks the application's certifi bundle; it does not replace unrelated
host/browser trust stores or prove every external certificate chain works.

Keep the full scan and migration evidence for the exact built image. A future
upstream update must rerun both; upgrading a tag alone is not qualification.
